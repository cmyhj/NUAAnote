# 第2章 ROS架构

## 学习目标

- 理解 ROS 架构的三个层次（OS层、中间层、应用层）

- 掌握 ROS 文件系统的组织结构

- 能够对比话题通信与服务通信的异同

## 2.1 ROS 架构设计

ROS 架构从两个角度各分为三个层次：

### 2.1.1 从运行角度的三层架构

```
┌─────────────────────────────┐
│         应用层               │
│  Master + 功能包节点          │
├─────────────────────────────┤
│         中间层               │
│  TCPROS/UDPROS 通信系统      │
│  机器人开发库（TF、运动控制等） │
├─────────────────────────────┤
│         OS层                │
│  Linux (Ubuntu)              │
└─────────────────────────────┘
```

**1. OS层**：ROS 依赖 Linux 操作系统，官方支持度最好的是 Ubuntu。也可运行在 macOS、Debian 等系统上。

**2. 中间层**：ROS 最核心的部分。
- 基于 TCP/UDP 封装了 **TCPROS/UDPROS** 通信系统
- 实现发布/订阅、客户端/服务器等通信模型
- 提供 Nodelet 进程内通信（适合实时性要求高的场景）
- 提供大量机器人开发库：数据类型定义、坐标变换、运动控制等

**3. 应用层**：运行 Master 管理器，管理整个系统。社区功能包以节点形式运行，以标准接口复用。

### 2.1.2 从系统实现角度的三层结构

| 层次 | 说明 |
|------|------|
| **计算图** | 运行时网络：节点、消息、话题、服务、Master |
| **文件系统** | 程序文件组织：功能包、功能包清单、消息类型、服务类型 |
| **开源社区** | 资源共享：发行版、软件源、Wiki、邮件列表、ROS Answers |

**随堂例题 2-1**（软件架构三层）

1. ROS 软件架构从下到上的三层顺序是？ A) 应用层→中间层→OS层  B) OS层→中间层→应用层  C) 中间层→OS层→应用层  D) OS层→应用层→中间层
2. ROS Master 位于软件架构的哪一层？ A) OS层  B) 中间层  C) 应用层  D) 硬件层
3. TCP/UDP 通信的二次封装位于哪一层？ A) OS层  B) 中间层  C) 应用层  D) 表示层
4. ROS 自身跨越了哪几层？ A) 仅中间层  B) OS层和应用层  C) 中间层(全部)+应用层(仅Master)  D) 全部三层

> **答案**：1.B  2.C  3.B  4.C

## 2.2 计算图

计算图是 ROS 运行时点对点网络的可视化描述。系统中的所有进程（节点）及其通信关系构成一张图。

### 2.2.1 节点（Node）

- **定义**：执行运算任务的进程，是 ROS 计算图的基本运行单元
- 一个机器人系统通常由数十到上百个节点组成（如摄像头驱动、激光雷达、SLAM 建图、路径规划、电机控制等）
- 节点间通过**话题**和**服务**进行通信
- 使用 `rosrun` 命令启动单个节点，使用 `roslaunch` 批量启动
- 使用 `rqt_graph` 可查看计算图

### 2.2.2 消息（Message）

- **定义**：节点间通信的数据载体，是一种严格的数据结构
- 支持标准数据类型（整型、浮点型、布尔型等）
- 支持嵌套结构和数组（类似 C 语言的 struct）
- 可由开发者**自定义消息类型**（`.msg` 文件）
- 常用标准消息包：`std_msgs`（标准类型）、`geometry_msgs`（几何类型）、`sensor_msgs`（传感器类型）

### 2.2.3 话题（Topic）与发布/订阅模型

- **话题**：节点间传递消息的通道，基于**发布/订阅**（Publish-Subscribe）模型
- **发布者（Publisher/Talker）**：向话题发布消息的节点
- **订阅者（Subscriber/Listener）**：从话题接收消息的节点
- 一个话题可有**多个**发布者和**多个**订阅者
- 发布者和订阅者**互不知晓对方的存在**

### 2.2.4 服务（Service）与客户端/服务器模型

- **服务**：基于**客户端/服务器**（Client/Server）模型的双向同步通信
- 包含两个部分的通信数据：**请求（Request）** 和**应答（Response）**
- ROS 中只允许有**一个**节点提供指定命名的服务

### 2.2.5 节点管理器（Master）

- ROS 系统的**核心协调者**，由 `roscore` 命令启动
- 通过 RPC 提供登记列表和查找功能，帮助节点找到彼此
- 提供**参数服务器**，管理全局参数
- **不参与实际数据传输**——节点建立连接后，数据传输直接进行

> **致命弱点——单点故障**：Master 一旦崩溃，新节点无法注册，新连接无法建立。ROS 2 通过 DDS 去中心化架构解决了此问题。

## 2.3 文件系统

### 2.3.1 功能包（Package）

功能包是 ROS 软件的基本单元，包含节点源码、库、配置文件等。典型结构：

```
my_package/
├── CMakeLists.txt      # 编译规则
├── package.xml          # 功能包清单（元信息）
├── src/                 # C++ 源代码
├── scripts/             # Python 脚本
├── include/             # 头文件
├── launch/              # 启动文件
├── msg/                 # 自定义消息类型
├── srv/                 # 自定义服务类型
├── config/              # 配置文件
└── action/              # 动作指令
```

### 2.3.2 功能包清单（package.xml）

包含功能包的元信息：名称、版本号、作者信息、许可信息、编译依赖（`<build_depend>`）和运行依赖（`<run_depend>`）。

### 2.3.3 元功能包（Meta Package）

将多个功能包整合为一个逻辑独立的功能包。只需要一个特殊的 `package.xml`（含 `<metapackage/>` 标签），不需要 `<build_depend>`。

### 2.3.4 常用命令

| 命令 | 功能 |
|------|------|
| `catkin_create_pkg` | 创建功能包 |
| `catkin_make` | 编译工作空间 |
| `rospack` | 查找功能包信息 |
| `roscd` | 跳转到功能包目录 |
| `rosls` | 列出功能包目录内容 |
| `rosrun` | 运行功能包中的节点 |
| `roslaunch` | 启动 launch 文件 |

## 2.4 开源社区

ROS 开源社区通过以下方式共享资源：

- **发行版（Distribution）**：带版本号、可直接安装的功能包集合
- **软件源（Repository）**：共享网络上的开源代码
- **ROS Wiki**：信息文档论坛（wiki.ros.org）
- **ROS Answers**：问答网站（answers.ros.org）
- **邮件列表与博客**：交流更新与发布新闻

## 2.5 ROS 的三种通信机制（⚠️ 考试重点）

### 2.5.1 话题通信机制（7 步）

话题通信基于**发布-订阅模型**，是 ROS 中最常用的通信方式，适用于**连续、高频的数据传输**（如传感器数据流）。

通信建立过程分为 **7 个步骤**——前 5 步为 RPC 阶段，后 2 步为 TCP 阶段：

```
RPC 阶段（前 5 步）—— 节点发现与元信息交换：
① Talker 注册：Publisher 通过 RPC 向 Master 注册（节点名、话题名、消息类型）
② Listener 注册：Subscriber 通过 RPC 向 Master 注册（节点名、感兴趣的话题名、消息类型）
③ Master 匹配：Master 根据话题名和消息类型匹配，将 Talker 的 RPC 地址发给 Listener
④ Listener 发送连接请求：Listener 通过 RPC 向 Talker 发送连接请求（传输协议、话题名、消息类型）
⑤ Talker 确认连接：Talker 通过 RPC 返回确认（含 TCP 连接参数）

TCP 阶段（第 6-7 步）—— 建立实际数据传输通道：
⑥ Talker 建立 TCP Server 等待连接
⑦ Listener 连接 Talker 的 TCP Server，建立连接后开始消息传输
```

**核心特点**：
- **异步性**：发布者不关心订阅者是否收到，不等待响应
- **多对多**：一个话题可有多个 Publisher 和 Subscriber
- **有缓冲区**：消息队列防止数据丢失（但可能导致延迟累积）
- Master 仅在建立连接时参与，**不参与最终数据传输**

> ⚠️ **考试关键**：记住"前 5 步 RPC，后 2 步 TCP；Master 参与前三步建立连接，不参与数据传输。"

**随堂例题 2-2**（话题通信 7 步）

1. 话题通信的建立共需要几步？ A) 3步  B) 5步  C) 7步  D) 9步
2. 话题通信 7 步中，前 5 步使用的通信协议是？ A) TCP  B) UDP  C) XML-RPC  D) DDS
3. 第 6-7 步使用的协议是？ A) RPC  B) TCP  C) UDP  D) HTTP
4. Master 参与话题通信的哪几步？ A) 第1-7步  B) 第1-3步  C) 第4-7步  D) 仅第1步
5. 话题通信第 1 步中，Publisher 调用什么函数向 Master 注册？ A) `subscribe()`  B) `advertise()`  C) `publish()`  D) `connect()`

> **答案**：1.C  2.C  3.B  4.B  5.B

### 2.5.2 服务通信机制（5 步）

服务通信基于**客户端-服务器模型**，是一次性的同步请求-响应，适用于**数据量小但有强逻辑处理**的场景。

通信建立过程分为 **5 个步骤**，全部基于 RPC + TCP：

```
① Talker 注册：Server 通过 RPC 向 Master 注册（节点名、提供的服务名）
② Listener 注册：Client 通过 RPC 向 Master 注册（需要查找的服务名）
③ Master 匹配：Master 查找匹配的服务提供者，将 Server 的 TCP 地址发给 Client
④ Client 连接 Server 并发送请求：Client 通过 TCP 连接 Server，发送请求数据
⑤ Server 返回应答：Server 执行服务功能后，向 Client 发送应答数据
```

**与话题通信相比**：少了 Listener→Talker 的连接请求和 Talker 确认连接这两个 RPC 步骤（相当于话题通信的第 4-5 步被合并了）。

### 2.5.3 参数管理机制（3 步）

参数服务器是 ROS 中的**全局变量**存储系统，由 Master 管理，**不涉及 TCP/UDP 通信**，全 RPC：

```
① Talker 设置变量：Talker 通过 RPC 向 Master 发送参数名和参数值
② Listener 查询参数值：Listener 通过 RPC 向 Master 发送参数查找请求
③ Master 返回参数值：Master 从参数列表中查找参数，通过 RPC 发送给 Listener
```

> **注意**：如果 Talker 更新参数值，Listener 不会自动获知——需要**动态参数更新机制**。

## 2.6 话题与服务的区别（⚠️ 考试必考）

| 对比维度 | 话题（Topic） | 服务（Service） |
|----------|--------------|----------------|
| 通信模型 | 发布/订阅（Publish-Subscribe） | 客户端/服务器（Client-Server） |
| 同步性 | **异步** | **同步**（请求后阻塞等待应答） |
| 通信步骤 | **7 步**（前 5 RPC + 后 2 TCP） | **5 步** |
| 连接关系 | 多对多 | 一对一（一个服务只能有一个 Server） |
| 数据流向 | 单向数据流 | 双向请求-应答 |
| 适用场景 | 连续、高频数据（传感器、控制指令） | 逻辑处理、参数查询等需要返回结果的场景 |
| 典型应用 | 激光雷达数据、摄像头图像、里程计 | 加法运算、删除乌龟、新生乌龟 |

## 本章小结

1. ROS 架构三层：**OS层**（Linux）→ **中间层**（TCPROS/UDPROS + 开发库）→ **应用层**（Master + 节点）
2. 计算图核心概念：**节点、消息、话题、服务、Master**
3. **话题通信 7 步**：前 5 步 RPC + 后 2 步 TCP，Master 不参与数据传输
4. **服务通信 5 步**：同步请求-应答，比话题少两个 RPC 步骤
5. **参数服务器 3 步**：全 RPC，不涉及 TCP/UDP
6. 话题是异步多对多，服务是同步一对一
7. 功能包是最基本的软件单元，package.xml + CMakeLists.txt 是核心配置文件
